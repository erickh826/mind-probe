### R4: Stale error after successful retry

During CONT2, the user returned from Offline to No throttling and reported
`285 uploaded / 0 failed`, while the old chunk-245 `Failed to fetch` error stayed
visible. The API continued receiving chunks. The final take had 530 consecutive
chunks and was complete; this was a stale error display, not evidence of a new
CORS failure or a missing chunk.

In [recordingController.ts at the reviewed head](https://github.com/erickh826/mind-probe/blob/169cb8fb0dbe50d8ca3a3334e7d065179a957a73/apps/student/src/recordingController.ts#L579),
chunk success acknowledges/deletes the queued chunk and updates counters, but
does not clear the transient error set by the catch path at line 637. Finalize
success can clear it later; recovery must work before Stop or F5.

Minimal regression, with a recording still running and no finalize:

1. Persist chunk 0 in IndexedDB; make its first upload fail with a transient error.
2. Confirm the error and failed count of one.
3. Make the same chunk retryable, then acknowledge it successfully and confirm
   server receipt.
4. Require two attempts, uploaded/failed/pending counts of 1/0/0 and no stale
   error. At `169cb8f` the last assertion fails.

The Student App owner should track error source and chunk sequence, clearing
only the matching recovered transient failure. Success for a different chunk
must not hide an outstanding failure. Preserve permanent conflicts, validation,
deletion and auth blocks, storage/recorder failures, `recorder_lost` and unrelated
finalize errors. `failedCount == 0` alone is insufficient because terminal
chunks are excluded from that counter.

Add the regression and preservation cases to the tracked
`apps/student/src/recordingController.test.ts`. The reviewer's local sidecar
is evidence, not a substitute for a committed product regression. Keep changes
inside `apps/student`; preserve sequence allocation, finalize payload and original
timestamp, retry timing, auth/grace rules and retention.
