## Proposed Administrator Workflow

### Sessions and Join Codes

1. Authenticate as an administrator.
2. Select an existing, validated case and create a session.
3. Display its ID and the Student, Wizard and Teacher join codes with copy

4. Show session status and provide explicit, audited management actions.
5. Support lost/consumed-code recovery only through a defined reissue contract;
   do not recover plaintext codes from storage or place tokens in URL queries.

2. Add the approved case documents, clip manifest, decision tree and rubric.
3. Upload media and check every referenced file and clip ID.
4. Validate the draft before making it selectable for training sessions.

validate case IDs before reusing any of that behavior.

## Recording grace on an existing database

`MINDPROBE_UPLOAD_GRACE_SYNTHESIZE_AFTER` decides whether the grace pass may
create a recording row for an ended session that does not have one. `POST
/sessions/{id}/end` always creates that row itself. A websocket `session_ended`
does not. The grace pass used to invent `incomplete` / `grace_expired` plus an
audit for every historical ended session the first time it ran.

This is a deployment choice. The process does not assume an installation date
and does not assume the database is fresh.

| Value | Meaning |
| --- | --- |
| Unset or blank | Existing-database default. Do not invent rows. Sessions that ended before this build keep no recording row and no new audit. |
| `fresh` | Synthesize a row for every ended session that lacks one. Set this only when the operator has confirmed the database was created with this build and has no earlier sessions. |
| ISO-8601 instant (`2026-10-20T00:00:00Z`) | Synthesize only when `ended_at` is at or after that cutover. Earlier sessions are left alone. Use the UTC instant this build is deployed, not a date baked into the source. |
| Anything else | Treated as unset. A warning is logged. No rows are invented. |

Rollout for a database that already has sessions: deploy with the variable
unset, confirm the grace thread is not rewriting old sessions, then set the
variable to the cutover instant and restart if post-cutover websocket ends
must be closed by grace. A brand-new database must set `fresh` explicitly if
that closure is wanted. Leaving it unset is safe; it is not an implicit
`fresh`.

## Vercel Assessment and Video Uploads

Updated 2026-10-14 after the user's hosting and upload clarification.

### Verified Platform Behavior

Vercel currently supports WebSockets in beta, including FastAPI/ASGI. Connections
close at the function's maximum duration, and separate connections or reconnects
can reach different instances. Durable state and inter-instance message routing
must therefore be external. See [Vercel WebSockets](https://vercel.com/docs/functions/websockets).

The existing `server/app/websocket.py` has a process-local `ConnectionManager`,
and `server/app/models.py` defaults to a local SQLite file. Merely deploying the
current FastAPI entrypoint would not establish correct cross-instance session
coordination or durable storage. FFmpeg processing and recording persistence also
need an explicit execution/storage design.

Ordinary Vercel Function request payloads are limited to 4.5 MB. Use authenticated
browser-to-storage uploads for case videos rather than posting large files through
a function. Vercel Blob supports this flow. See [Function limits](https://vercel.com/docs/functions/limitations)
and [client uploads](https://vercel.com/docs/vercel-blob/client-upload).

### Recommended Initial Architecture

- Vercel: production frontend apps and administrator interface.
- One persistent FastAPI process with durable storage: live session coordination,
  SQLite, authorization, recording ingest and FFmpeg processing. Do not add
  multiple backend workers until session state/broadcasting is shared.
- Object storage, with Vercel Blob as a candidate: uploaded case videos. Keep
  student recordings private under the existing role-based access requirements.
- Resolve HTTPS, cookie scope, API routing and WSS routing together and verify
  them from a separate browser/device before rollout.

This recommendation minimizes changes to the existing runtime architecture; it
is not a claim that Vercel cannot host WebSockets. An all-Functions migration
would additionally need an external database, shared session state/pub-sub,
durable object storage and a verified media-processing execution path.

### Upload Acceptance Scope

- Authenticated administrators select a case and upload one or more videos with
  progress, failure feedback and retry controls.
- Server authorization binds the upload to a case and permitted object path,
  limits size/content types and never exposes a storage master credential.
- Completion is verified on the server before publishing a clip reference;
  client-supplied URLs alone are not proof of a successful authorized upload.
- Uploaded media is validated for usable format/duration, previewed, and mapped
  to clip IDs and decision-tree entries before the case becomes playable.
- Incomplete uploads and duplicate filenames do not silently replace published
  clips or alter a case used by an active session.
- Public versus private case-video access must be chosen explicitly. Vercel
  public Blob URLs are readable by anyone with the URL; private stores require
  authenticated delivery. See [Blob security](https://vercel.com/docs/vercel-blob/security).
- Upload credentials are separate from Student/Wizard/Teacher join codes; case
  authoring does not give participants administrator access.
