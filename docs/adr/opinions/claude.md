# Mind-Probe 架構辯論：三大爭議點的立場文件（Claude opinion）

> 依據：[`mindprobe_spec_v1_final.md`](mindprobe_spec_v1_final.md)（v1.0 最終規格，含審閱修訂）。
> 本文目的：對三個尚未定案的架構問題，給出**明確、可執行、不迴避取捨**的立場，供工程團隊辯論與定案參考。凡與規格既有決定衝突之處，會明確指出「我認為規格這裡應該修改」。

## 議題一：WebSocket 架構與斷線重連機制

### 建議做法（具體做法）

**連線拓樸：星狀，Session Server 為唯一權威中心，不做 P2P。**

- Wizard 控制台與學生端**各自**與 Session Server 建立獨立 WebSocket 連線（`/ws/wizard/{session_id}?token=...`、`/ws/student/{session_id}?token=...`），彼此不直連、不透過 WebRTC data channel。規格第四節已隱含此設計（兩端都連 Server），這裡是明確反對任何「Wizard 直接推流給學生端」的簡化提案——原因見下方風險分析。
- Server 端維護一個 **per-session 的 `ConnectionManager`**，內部資料結構：
  ```python
  class SessionConnection:
      session_id: str
      wizard_ws: WebSocket | None
      student_ws: WebSocket | None
      event_log: list[Envelope]       # 權威事件序列，append-only
      next_sequence: int
      last_wizard_seq_acked: int
      last_student_seq_acked: int
      clock_offset_student_ms: int
      clock_offset_wizard_ms: int
  ```
  重點：**事件的權威來源（source of truth）是 Server 的 `event_log`，不是任一端的記憶體狀態。** Wizard 端按熱鍵只是「送出意圖」，Server 蓋上 `sequence` 與 `server_timestamp_ms` 後才是正式事件，再廣播給雙方。這與規格第九節「Server 建立 session_id...所有事件同時保存」的精神一致，我這裡把它明確為架構規則：**任何一端都不能對事件序號做假設性推進，只能等 Server ack。**

**心跳（heartbeat）節奏：雙向 ping，3 秒一次，9 秒無回應判定斷線。**

- 具體數字：Server 每 3 秒對兩端各發一次 `ping`（含 `server_timestamp_ms`），客戶端立即回 `pong`（回帶原始 timestamp）。連續 3 次（9 秒）未收到 pong 才判定斷線並觸發重連 UI 提示。
- 為什麼是 3 秒而不是業界常見的 30 秒（如一般 Web 應用）：這是一個**即時互動系統**，Wizard 按鍵到影片播出的驗收目標是中位數 < 400ms（規格十四節）。如果心跳週期用 30 秒，斷線後最多要等 30–90 秒才發現，對一個 10–15 分鐘的 session 是災難性的（等於少了 5–15% 的可用時間在「不知道已經斷線」的狀態）。3 秒/9 秒的代價是多一點點頻寬（在同一區網內完全可忽略），用極小成本換取快速斷線偵測，這筆帳非常好算。

**重連與事件補送：以 `sequence` 為斷點，Server 主導重放，不是客戶端主導重建狀態。**

- 客戶端（無論 Wizard 或學生端）重連時，在 WebSocket handshake 之後第一件事是送 `{"type": "resume", "session_id": ..., "last_seen_sequence": N}`。
- Server 收到後，從 `event_log` 中找出 `sequence > N` 的所有事件，**依序**重新推送（不是只推最新狀態）。這點很關鍵：如果只送「目前狀態」（例如目前播放中的 clip），教師回看與資料完整性會出問題，因為中間可能有 `clip_interrupted` 這類轉場事件被跳過，導致後續分析時事件鏈不連續。**寧可多送幾筆重複可忽略的事件，也不要漏事件。**
- 客戶端必須做**去重**：每個事件帶全域唯一的 `sequence`（規格已定義），客戶端套用事件前檢查是否已處理過該 `sequence`，是則丟棄。這是防止「重連時序競態」導致同一個 `clip_started` 被套用兩次、影片重播的必要手段。

**Session-level token 設計：Server 產生的隨機 opaque token，綁定角色（role-scoped），不做真正的使用者驗證。**

- 規格修訂 6 已提出 session-level token 概念，我認為需要更精確：**應該是三個獨立 token，不是一個共用 token。** 即 `wizard_token`、`student_token`、`observer_token` 各自不同，Server 在建立 session 時一次性產生（例如 UUID4），列印/顯示在啟動畫面供對應角色輸入。
- 理由：如果三端共用一個 token，任何一端的 token 外流（例如投影到房間裡讓觀察員抄到）就等於拿到全權限，可以偽裝成 Wizard 對正在進行的 session 下指令。分角色 token 的成本幾乎是零（只是多產生兩個字串），但避免了「學生不小心看到同一個 token 就能連上 Wizard 通道亂按」這種在教室/實驗室環境下真實會發生的情境。
- 這不是身份驗證，是**存取範圍限制**，符合 MVP 的目的（規格明說是「避免同網段其他裝置誤連或窺看」，不是防範惡意攻擊者）。不需要 JWT、不需要過期機制、不需要 refresh token——這些都是過度工程。Session 結束後 token 直接在 Server 記憶體/DB 中失效即可。

### 主要風險與取捨

1. **風險：Server 是單點故障。** 如果 Session Server process 掛掉，Wizard 和學生端同時失去連線，且 `event_log` 若只存在記憶體會直接消失。
   **取捨決定：`event_log` 每筆事件寫入時同步落地 SQLite（不是只留在記憶體），Server 重啟後可以從 DB 恢復 session 狀態並允許雙端重連恢復。** 這犧牲了一點點寫入延遲（SQLite 單筆 insert 在區網內本機通常 <5ms，遠低於 400ms 預算），換來的是「Server 短暫重啟不等於整個 session 報廢」。我認為這個取捨是必須的，不是可選項——規格十四節本身就要求「系統崩潰後可恢復錄影，最多損失最後4秒」，Server 端事件也該有對等的耐久性保證。

2. **風險：3 秒心跳在真正網路壅塞時可能誤判斷線（false positive）。** 區網內理論上不該發生，但如果同網段有人在跑大量檔案傳輟（例如影片庫更新），仍有可能瞬間延遲。
   **取捨：接受這個風險，因為誤判的代價遠低於漏判的代價。** 誤判斷線只是觸發一次不必要的重連流程（有去重機制保護，不會造成資料錯誤，只是 UI 上短暫閃一下「重新連線中」），而漏判斷線（心跳太鬆）會讓 Wizard 對著一個實際上已經斷線的介面按熱鍵，學生端毫無回應卻沒人知道發生了什麼——這對一個正在進行的訪談是嚴重得多的失敗模式。

3. **取捨：不做客戶端狀態機自主決策，一切等 Server 確認。** 這會讓系統在網路好的時候「感覺」比純客戶端樂觀更新慢一點點（因為 Wizard 端要等 Server ack 才真正顯示「已送出」），但换來的是**教師回看資料的絕對一致性**——這是規格明訂的第二優先開發項目（「學生錄影與疑犯事件能否可靠同步及保存」），我認為在「反應速度的手感」與「事後資料完全可信」之間，後者的優先級必須更高，因為這是研究型 MVP，資料品質直接決定整個專案能不能撐到第二版。

### 具體理由

這套設計的核心哲學是：**Server 是唯一真相來源，客戶端永遠是「觀察者+意圖提交者」，不是「狀態決策者」。** 這在分散式系統設計裡是標準做法（類似 Raft/Paxos 系統裡的 leader-based log replication，只是這裡簡化到單一 leader 沒有容錯需求，因為 MVP 階段只有一台 Server）。選擇這個模式而非「客戶端各自維護狀態、靠廣播同步」的原因很直接：後者在斷線重連時極難保證一致性，一旦 Wizard 端和學生端的本地狀態在斷線期間分岔，重連後誰的版本是對的？用事件序號+Server 權威日誌可以完全避免這個問題類別，用架構設計把整類 bug 消除掉，而不是靠測試去抓。

### 信心程度：**高**

這是相對成熟的模式（事件溯源 + 心跳 + sequence-based resume），在區網、單 Server、10–15 分鐘 session 的規模下沒有任何規模化風險需要擔心。唯一的不確定性是心跳間隔的具體數字（3 秒/9 秒）是否要根據 mini-pilot 實測調整，但這個機制本身的正確性我有很高信心。

### 是否有更好的替代方案？

有一個值得考慮但我**不建議**在初版採用的替代方案：**用 Server-Sent Events (SSE) 取代 WebSocket 做 Server→Client 的單向廣播，只用 HTTP POST 做 Client→Server 的指令。** 這樣可以用瀏覽器原生重連機制（SSE 內建 `Last-Event-ID` 自動重連語意，剛好對應到我們的 `sequence` 概念）省掉自己寫重連邏輯。
但我不建議切換，理由：(1) 規格已經定案用 WebSocket，且第四節架構圖與教學/文件已經圍繞這個假設；(2) Wizard 端是雙向高頻互動（熱鍵送出＋接收確認＋接收心跳），SSE 只能單向，Wizard→Server 那條路還是要另開 HTTP，等於兩套機制並存，複雜度不降反升；(3) 團隊時間有限（8–10 週技術 MVP），臨時改架構的風險大於收益。**這是「理論上更優雅但不值得現在換」的例子，維持 WebSocket 是對的決定。**

## 議題二：Fallback 機制設計

### 建議做法（具體做法）

**分兩層 fallback：Wizard 主動選擇的「通用 Fallback 片段」是第一層，不是真正的異常處理；「標記未覆蓋問題＋事後擴充」才是真正解決問題的機制。**

規格已經在第六節配了 4 段「通用Fallback」影片（要求澄清、不明白、不記得、拒答），第八節有 `F` 熱鍵、`M` 熱鍵（標記未覆蓋問題）。我認為這個框架方向是對的，但需要補上具體判斷邏輯與升級路徑：

1. **Wizard 端決策流程（當學生問題沒有直接對應的案件專屬回答時）：**
   - Step 1：Wizard 在 3 秒思考片段（Thinking clip 播放期間）內快速判斷，這問題屬於「有點沾邊但不精確」還是「完全問到案件庫沒有的東西」。
   - Step 2a（沾邊但不精確）：選最接近的案件專屬回答，即使不是 100% 對題——**這是有意的設計，我主張優先於播放通用 fallback**。理由見下方「主要風險」。
   - Step 2b（完全沒有對應內容）：播放通用 Fallback 中最貼切的一段（「不明白」vs「不記得」vs「拒答」——這三者語意不同，Wizard 要在 1 秒內選對，這對熱鍵佈局有要求，建議把這 4 個 fallback 熱鍵獨立於 F1–F8 分類之外，直接放在鍵盤數字排最外側，例如 `9`、`0`、`-`、`=`，確保永遠可以「盲按」不需要切換分類層）。
   - Step 3（**必做**）：無論走 2a 或 2b，只要 Wizard 認為這是「案件庫本應該覆蓋但沒覆蓋」的問題，一律按 `M` 標記。這個標記本身要帶上：目前案件階段、學生剛問的問題（用 Wizard 打字備註或事後 ASR 回填）、Wizard 當時選了哪個替代片段。

2. **升級路徑（escalation path）具體設計：**
   - **Session 內不升級給真人介入**——我明確反對任何「這時候切到 Wizard 直接用麥克風講話代替疑犯」的提案（即使技術上用 WebRTC 可以做到）。規格已經把「即時 TTS」和「聲音一致性」列為明確排除項（第十一節），如果 Wizard 用真人聲音介入，等於當場打破人物一致性，比播錯一段影片更破壞沉浸感，且會污染資料（教師事後看錄影會看到疑犯聲音忽然變成另一個人）。**遇到真的答不上來的問題，寧可讓學生「撞牆」（疑犯用拒答/不明白片段擋回去），也不要真人跳進來救場。** 這是初版 MVP 刻意的取捨，讓 Wizard 練習「在約束下工作」也是研究資料的一部分（Wizard 選錯/答不上的頻率本身就是規格十四節要追蹤的研究指標）。
   - **跨 session 升級：** 每次 `M` 標記的資料，在每天/每次 pilot 結束後彙總，形成「待補片段清單」，依規格第十七節的擴展門檻邏輯，累積到一定量後才拍新片段、擴充影片庫（規格已有此機制，我完全同意，不重複展開）。

3. **Fallback 片段選擇的具體演算法（不要用 AI/分類器，用簡單規則）：**
   - MVP 階段**不建議**做任何自動判斷「該用哪個 fallback」的邏輯，這完全交給 Wizard 人腦判斷，理由是規格開篇就定義這是「Wizard 人工控制」的 MVP，加自動分類器是第二版的範疇（規格第十七節已經寫明），這裡不應該提前引入。我要辯論的對象若主張「至少做個關鍵字比對來提示 Wizard」，我的立場是：**不要**，因為關鍵字比對在廣東話口語、審訊情境下精準度低，錯誤提示比沒有提示更容易誤導 Wizard 選錯（規格十四節本身就把「Wizard選錯影片」列為要追蹤降低的指標，貿然加一個不準的提示系統只會讓這個數字更差）。

**WebSocket 斷線時學生端行為：必須獨立於伺服器連線狀態繼續錄影與本地緩衝，這是不可退讓的硬性需求。**

- 具體實作：學生端的 `MediaRecorder` 啟動邏輯**不能**掛在 WebSocket 連線狀態上。即：`mediaRecorder.start(2000)` 應該在 session 開始時啟動，只在使用者主動按下「結束 session」或發生瀏覽器層級的致命錯誤時停止，WebSocket 斷線、重連、甚至完全斷線 30 秒，都不該觸碰錄影邏輯。
- Chunk 上傳這條路徑本來就已經設計成 IndexedDB 佇列＋背景重試（規格修訂 5），這意味著**錄影與上傳本來就是解耦的**——我在這裡要做的只是把這個解耦原則明確延伸到「錄影啟動/停止」本身，不只是「上傳失敗重試」。目前規格文字沒有明講「斷線期間錄影是否繼續」，這是我認為需要補上的明確條款：**答案是必須繼續，沒有模糊空間。**
- 學生端 UI 在斷線期間應顯示「連線中斷，錄影持續進行中」而不是把畫面卡住或顯示錯誤全螢幕遮罩——如果學生因為 UI 誤導而以為錄影已經停止，可能會做出不自然的行為（例如停下來等、或詢問工作人員），直接污染這次資料。

### 主要風險與取捨

1. **風險：Step 2a「選最接近但不精確的案件回答」可能造成事實矛盾。** 規格十四節有一條硬指標「案件事實矛盾：0次」。如果 Wizard 為了避免用生硬的 fallback，硬選了一個相近但語意上暗示了不同時間線/證據的答案，可能觸發事實矛盾。
   **取捨決定：我仍然主張優先 2a，但加一個安全閥——`clip_manifest.json` 裡已有 `forbidden_after` 欄位（規格十二節），這個機制必須在 Wizard 控制台做即時過濾：任何會與已揭露事實衝突的候選片段，UI 上直接不顯示/反白鎖定，不讓 Wizard 誤按。** 有了這道機制，「選相近片段」的風險就從「可能導致事實矛盾」降到「可能語意上有點勉強但不違反事實」，這是可以接受的品質妥協，換來的是大幅降低通用 fallback 的使用率（通用 fallback 感覺很生硬、重複用幾次學生就會察覺是罐頭回答，破壞沉浸感）。這比「事實矛盾」的風險等級低很多，值得用 `forbidden_after` 過濾機制去對沖。

2. **風險：學生端本地持續錄影＋緩衝，如果 session 拖很久斷線（例如斷線 5 分鐘以上才恢復），IndexedDB 佇列可能累積大量未上傳 chunk，造成瀏覽器記憶體/儲存壓力，且 session 結束時"確認全部上傳成功"的等待時間可能很長。**
   **取捨：接受這個風險，且不建議做「斷線太久就丟棄本地錄影」這種妥協**——录影資料是整個系統最重要的產出（規格明訂第二優先開發項目就是「學生錄影與疑犯事件能否可靠同步及保存」），寧可讓學生端多等幾分鐘上傳、寧可介面上顯示「上傳中，請勿關閉」擋住結束流程,也不要因為怕儲存壓力而丟資料。10–15 分鐘 session 的 WebM chunk 總量（2 秒一段，一般網路攝影機畫質）在現代瀏覽器 IndexedDB 容量限制下完全不成問題，這個風險被高估，不需要為此犧牲資料完整性。

3. **取捨：不做 session 內真人語音介入的升級路徑，代價是某些完全脫稿的訪談會「卡」。** 我承認這會讓少數 session 的體驗變差（學生問了一個完全出乎意料的問題，Wizard 只能讓疑犯裝傻擋回去，學生可能覺得訪談不夠真實）。但這正是 MVP 想驗證的東西之一——規格明訂「預製影片能否支援基本自由對話」是研究問題本身，不是要先解決的 bug。如果初版就用真人介入打補丁，反而測不出「純預錄片段庫」這個假設到底可行到什麼程度，會污染研究資料的意義。

### 具體理由

Fallback 設計的核心原則是：**把「片段不夠用」當成研究要收集的訊號，而不是要在架構層消除的 bug。** 規格自己在第十四節把「Fallback率」「未預期問題」列為要記錄分析的研究指標，這代表產品邏輯早已認同「Fallback 會發生、發生是正常且有價值的」。我的立場只是把這個邏輯貫徹到底：不要在 MVP 裡試圖用技術手段（AI 分類器、真人介入、即時 TTS）去「解決」fallback，那些都是規格明確排除的範疇，且會弄髒研究資料。真正該做的架構投入，是確保 (a) fallback 發生時不違反事實一致性（`forbidden_after` 過濾）、(b) 每次 fallback 都被完整記錄可供事後分析、(c) 錄影本身完全不受 fallback 或連線問題影響。

### 信心程度：**高**（錄影獨立於連線狀態）／**中**（fallback 選擇優先 2a 而非直接跳 2b）

「錄影必須獨立於 WebSocket 狀態」這一條我信心非常高，這幾乎沒有爭議空間，任何讓錄影依賴即時連線的設計都是脆弱架構。
「優先選相近案件片段而非直接跳通用 fallback」這條信心中等，因為這個判斷高度依賴 Wizard 的臨場判斷力與 `forbidden_after` 規則庫覆蓋得夠不夠完整，如果 mini-pilot 發現 Wizard 頻繁選錯造成矛盾，我會願意修正為「不確定時優先用通用 fallback，寧可生硬也不要冒事實矛盾風險」。這是我認為最值得在 mini-pilot 後用真實數據重新檢視的一條立場。

### 是否有更好的替代方案？

有。**我認為規格目前對「案件專屬回答」與「通用Fallback」的二元劃分可以再加一層：「相近但標記為 approximate 的過渡片段」。** 具體做法：在 `clip_manifest.json` 加一個 `is_approximate_fallback: true` 標記，讓部分案件專屬片段可以同時被歸類成「這題答不太準但語氣自然」的候選,專門給 Wizard 在 2a 情境使用，且這類使用會自動觸發跟 `M` 標記一樣的記錄（不需要 Wizard 額外按鍵，Server 端可以從「選用了帶 approximate 標記的片段」自動推斷這是一次隱性 fallback）。這樣可以拿到比純手動 `M` 標記更完整的 fallback 使用資料（因為人在忙碌時容易忘記按 `M`），且不需要新增影片,只是給既有的 12 段案件專屬片段加中繼資料標記。這個方案我認為優於原規格的做法,但因為只是資料模型的小擴充,不影響架構,建議可以晚一點再加,不阻塞 MVP。

## 議題三：時間同步機制

### 建議做法（具體做法）

**Clock offset 估算：NTP 風格的多次 ping/pong，建議 7–9 次往返，取樣後用 median 而非 average，並用往返延遲（RTT）做離群值過濾。**

具體演算法：

1. Session 建立階段（在正式開始訪談前，學生端與 Wizard 端各自）向 Server 發送 `sync_ping`，內容為 `{client_send_ts: T0}`。
2. Server 立即回 `sync_pong`，內容為 `{client_send_ts: T0, server_recv_ts: T1, server_send_ts: T2}`。
3. 客戶端收到後記錄 `client_recv_ts: T3`，可以算出：
   - RTT = `(T3 - T0) - (T2 - T1)`
   - 該次估算的 clock offset = `((T1 - T0) + (T2 - T3)) / 2`（標準 NTP 公式，假設上下行延遲對稱）
4. **重複 7–9 次**（不是規格原文含糊的「多次」——我明確主張至少 7 次，理由見下），每次間隔約 200–300ms 避免瞬間網路自我干擾。
5. **過濾**：先按 RTT 排序，**丟棄 RTT 最大的 2 筆**（這些代表當時網路瞬間壅塞、offset 估算最不準的樣本），剩下的樣本取 **offset 的 median**，不是 average。
6. 最終 `clock_offset_ms` 就是這個 median 值，寫入 session 的 `SessionConnection.clock_offset_student_ms` / `clock_offset_wizard_ms`,供後續每個事件套用（規格第九節事件封套裡的 `clock_offset_ms` 欄位）。

**為什麼是 median 不是 average，這是本節最重要的立場：**
Average 對離群值極度敏感——區網內即使整體延遲很低（1–5ms），偶爾一次因為系統排程/GC/瀏覽器 tab 切換造成的 50ms 尖峰延遲,會直接把 average 拉偏,而且**這種尖峰通常是不對稱的**（只影響某一次往返的其中一段路徑,不是均勻分佈),NTP 演算法假設對稱延遲的前提在那一次樣本上就是錯的。用 median 可以讓少數幾次失準的樣本完全不影響最終估算,只要多數樣本（比如 7 次裡有 5 次）延遲正常對稱,median 就會落在正確值附近。這在學術網路時間同步文獻裡是標準做法（不是我發明的),regspec 裡「多次ping/pong估算」這句話沒說清楚統計方法,我認為這裡必須明確釐清,否則不同工程師可能各自實作 average,導致實測結果不穩定又難 debug。

**為什麼是 7–9 次，不是 3–5 次或 15+ 次：**
- 太少（3–5 次）：離群值過濾後剩下的樣本太少（丟 2 筆離群值後只剩 1–3 筆），median 統計意義薄弱,一次不巧的異常值就可能污染結果。
- 太多（15+ 次）：session 開始前的同步階段本身佔用時間,而區網內的 offset 在沒有大幅時鐘漂移的前提下,多測沒有實質收益,只是拖長學生等待開場的時間（這對研究情境的體感很重要——規格希望訪談自然,如果開場要等 10 秒鐘做時間同步,體驗會變差）。
- 7–9 次是一個經驗上合理的甜蜜點：丟 2 筆離群值後仍有 5–7 筆有效樣本,统计上足够稳健,整個同步階段耗時在 2–3 秒內可以完成（間隔 250ms × 9 次 ≈ 2.25 秒),學生完全感覺不到延遲。

**Drift correction（10–15 分鐘內的時鐘飄移校正）：初版不需要連續動態校正，但需要一次「session 中段補測」作為保險。**

- 我的立場：**在區域網路、10–15 分鐘的時間尺度內，瀏覽器/伺服器的系統時鐘漂移量微乎其微（現代作業系統的時鐘漂移通常是 ppm 級別,15 分鐘內累積誤差遠低於 1ms),完全不需要做連續的 drift correction 演算法（例如複雜的線性回歸擬合 clock skew）。** 這是我要明確反駁的一種可能提案——如果有工程師主張要做「連續追蹤 clock skew 並動態調整」,我認為這是**過度工程**,在這個時間尺度和網路環境下,投入的複雜度與實際能改善的準確度不成比例,且會讓 debug 變困難（動態校正的系統比一次性校正的系統難驗證正確性）。
- 但我建議加一個**低成本的保險機制**：在 session 進行到約 7–8 分鐘（中點）時,背景自動重跑一次同樣的 7 次 ping/pong 流程（不打斷任何互動,純背景),得到第二個 offset 估算值。如果與初始值的差異超過 50ms（這已經遠超正常區網漂移範圍),就記錄一個 warning 事件並保留兩個 offset 值供事後分析選用較準確的一段;如果差異在 50ms 內（預期會是常態),就什麼都不用做,初始值持續有效到 session 結束。這個機制的成本極低（背景 2 秒的網路流量),但可以在異常情況下（例如 Wi-Fi 訊號忽然變差、Server 主機忽然吃重負載）提供一個事後可稽核的訊號。

**<300ms 同步準確度目標：可行，且區網環境下應該可以做到遠優於此（實際能到 20–50ms 級別），但要說清楚"300ms"這個數字實際包含了什麼。**

這裡我要挑戰規格對這個指標的表述方式。規格十四節寫「錄影與事件同步誤差低於300ms」,把這個當成單一數字,但實際上誤差來源至少有三個獨立部分,必須分開討論才有意義:

1. **Server-Client clock offset 估算誤差**：用上述 7–9 次 ping/pong + median 演算法,在區網（RTT 通常 <5ms）下,offset 估算誤差通常在個位數到 20ms 之間,這部分完全在預算內,非常寬裕。
2. **事件時間戳記與影片實際播放時間的誤差**：Wizard 按熱鍵 → Server 蓋章 → 廣播給學生端 → 學生端瀏覽器接到訊息 → `<video>` 元素實際開始播放,這中間有網路傳輸 + 瀏覽器事件迴圈排程 + video decode 啟動延遲,這部分才是主要的不確定性來源,而且**這部分跟 clock offset 演算法完全無關**,offset 估算再準,如果影片解碼啟動要 100–200ms,同步誤差還是會有這個量級。
3. **學生錄影 chunk 的時間戳記與實際畫面內容的對應誤差**：`MediaRecorder` 的 chunk 邊界時間與實際錄到的畫面之間也有瀏覽器實作相關的小誤差。

**我的立場：<300ms 這個目標對「clock offset 估算」（第1部分）來說太寬鬆了（用心跳頻率為3秒配上上述演算法,可以做到誤差在 50ms 內),但對「事件到實際影片畫面出現」的端到端誤差（第2部分）來說是合理甚至有點緊張的目標,需要靠雙播放器預載機制（規格已有此設計）來壓低影片啟動延遲,不能只靠時間同步演算法解決。** 換句話說,300ms 這個驗收指標,考驗的其實主要是「雙播放器預載＋WebSocket 傳輸延遲」的工程,不是「clock offset 演算法」本身——這一點我認為規格應該在驗收標準裡拆開寫,不然團隊會誤以為只要把 ping/pong 演算法做好這個指標就達標,實際上大部分風險在别的地方。

**備用 tone+flash 同步法：可靠，但只適合當「離線稽核用的最後防線」，不該被賦予比它適合的更高期待。**

- 規格第九節的備用同步法（session 開始時同步播放提示聲＋畫面閃白,備用攝影機同時拍到）本質上是給**離線、事後、人工對齊**用的,可靠性評估要分兩層:
  - **作為「備用攝影機與主錄影對齊」的手段：非常可靠。** 聲音瞬間（click/beep）與畫面閃白在人眼/人耳/後製軟體上都極容易精準辨識到個位數毫秒級,這是傳統影視後期同步的標準做法（拍板/場記板原理相同),技術上沒有任何疑慮。
  - **作為「持續糾正 WebSocket 時間同步」的手段：不適合,且規格沒有這樣要求,但我要主動澄清避免有人誤用。** Tone+flash 只在 session **開始那一刻**做一次,它不能也不該被期待去糾正 15 分鐘後的漂移——但如前面分析,15 分鐘內的漂移本身就微乎其微,所以這不構成問題,只是要明確這個方法的定位:它是「一次性錨點,给備用錄影用」,不是「持續同步機制」,兩者不要混為一談。
- 我認為現有設計已經足夠,不需要加碼（比如有人可能會提議在 session 中段也閃一次白幕做二次錨點）——**這樣做反而會打斷訪談的沉浸感（畫面忽然閃白,學生會出戲問「發生什麼事」),代價大於收益。** 備用攝影機唯一的用途是「主錄影失敗時的救援」（規格十.2 已寫明,「不必進入自動分析流程」),既然不需要自動分析對齊的精確度,一次性錨點完全夠用。

### 主要風險與取捨

1. **風險：median 演算法在極端情況下（例如 7 次樣本中有 4 次都是離群值）仍可能失準。** 這種情況理論上可能發生於網路狀況真的很糟的區網環境。
   **取捨：加一個健全性檢查（sanity check）而非更複雜的統計方法** ——如果 9 次樣本裡 RTT 的標準差超過某個絕對值門檻（例如 30ms,在區網內這已經是明顯異常),就在 UI 上對主持人顯示「網路狀況不穩定,時間同步可能不準確」的警示,讓人工介入決定是否要重跑或换網路,而不是試圖用更複雜的演算法自動修正一個本質上是網路品質問題（不是演算法問題）的狀況。**這是刻意的簡化取捨**：把「網路真的爛」的邊界情況交給人工判斷,而不是為了應付這個低機率情境去過度設計演算法本身,保持系統的可理解性。

2. **風險：把 300ms 目標簡化理解為「只要 offset 演算法準就達標」,導致團隊對真正的風險來源（影片啟動延遲）投入不足。**
   **取捨：我建議在驗收測試階段,把這個單一指標拆成上述三個子項分別量測**（可以用簡單的做法:錄下畫面上的系統時鐘顯示＋螢幕錄影,量測 Wizard 按鍵時刻到畫面實際變化時刻的差異),這樣多花一點測試設計的功夫,但能避免「指標達標但沒人知道為什麼」或「指標不達標但不知道該優化哪裡」的情況。這對一個以「收集後續自動化所需資料」為目標的研究型 MVP 來說,測量方法的嚴謹度本身也是產出的一部分,值得投入。

3. **取捨：不做連續 drift correction,只做中點一次性複測。** 代價是如果真的發生罕見的系統級異常（例如 Server 主機在 session 中途被其他行程搶佔導致系統時鐘被 NTP 大幅修正——這在容器化部署環境偶有發生),初版機制只能事後從中點複測的 warning 事件發現,不能即時糾正當下正在錄製的事件時間戳。**我認為這個取捨可以接受**,因為:(a) 這類事件發生機率在受控的 pilot 環境下極低,(b) 就算發生,規格本身允許事後用備用攝影機的 tone+flash 錨點做人工對齊救援,不會導致資料完全報廢。為了一個低機率、有替代救援手段的情境去增加系統複雜度,不符合 MVP 的精神。

### 具體理由

整體策略是：**用統計上站得住腳但計算簡單的方法（median + 離群值過濾）解決 clock offset 問題,把「持續動態校正」這種在此情境下收益極小的複雜度直接砍掉,同時明確指出 300ms 這個驗收指標的風險大頭其實不在時間同步演算法,而在雙播放器的啟動延遲工程。** 這個立場背後的一貫邏輯,和議題一、二一样：**在 MVP 階段,面對「可以簡化但正確」與「複雜但邊際收益低」之間的選擇,永遠選前者,把有限的工程時間留給真正影響驗收指標的地方（影片預載、Wizard 決策流程),不要把時間花在打磨一個本來就不是瓶頸的子系統。**

### 信心程度：**高**（median 優於 average、不需連續 drift correction）／**中**（7–9 次的具體數字）

Median 統計方法優於簡單 average 這一點,在有離群值風險的網路量測情境下是業界共識,信心很高。不需要連續 drift correction 這一點,基於區網＋15分鐘時間尺度的物理現實,信心也很高。
「7–9 次」這個具體次數,是基於一般經驗法則的合理估計,但沒有針對這個特定部署環境（教室區網、特定路由器/交換機）做過實測,如果 mini-pilot 階段實測發現區網延遲波動比預期大,我願意調整到 11–13 次,這個數字本身信心中等,演算法框架信心高。

### 是否有更好的替代方案？

有一個值得一提但**不建議在 MVP 使用**的替代方案：**用 WebRTC data channel 的內建往返時間量測機制,或改用瀏覽器 Performance API 配合 `navigator.serverTiming` 之類的瀏覽器層級高精度計時工具,取代手工實作的 ping/pong。** 這類工具在理論上可以提供更高精度的時間戳（微秒級,而非 JS `Date.now()` 的毫秒級)。
不建議的理由：(1) 規格已明訂 WebRTC「非核心，只在Wizard需要遠端監聽時加入」,不應該為了時間同步這個子問題引入額外技術棧;(2) 300ms 的目標對毫秒級精度的 `Date.now()` 已經有超過一個數量級的餘裕,微秒級精度是解決一個我們根本沒有的問題;(3) 手工 ping/pong 演算法簡單、透明、容易 debug 與向團隊解釋,這在一個時程緊湊（8–10週）且需要向非工程背景的審閱者（教師、研究者）解釋系統運作方式的專案裡,是一個被低估的優勢。**維持簡單的手工 NTP 風格演算法是正確決定，不需要更「先進」的工具。**

| Fallback 機制 | 優先選相近案件片段而非直接跳通用fallback（配合`forbidden_after`過濾）；不做session內真人介入升級；錄影必須完全獨立於WebSocket連線狀態，斷線也要繼續錄 | 錄影獨立性：高／fallback優先順序：中 |
| 時間同步 | 7–9次ping/pong取median非average；不做連續drift correction，僅中點一次性複測作保險；300ms指標的風險大頭在影片啟動延遲而非offset演算法本身 | 高（統計方法與不做連續校正）／中（具體次數） |
