# 錄影與補傳操作手冊

## 適用範圍

適用於 `feat/m2` 現行版本（`032e64e`），亦即目前部署的版本。錄影完整性、補傳碼和寬限期由
[PR #2](https://github.com/erickh826/mind-probe/pull/2) 加入（2026-10-26 合併為 `967c246`）；
OP 管理頁（#13、#14）及管理員登入（#20、#21）之後才加入。PR #2 的驗收證據已移到
[`archive/2026-10-pr2-recording-acceptance.md`](archive/2026-10-pr2-recording-acceptance.md)。

2026-10-21 的 D12 原採 (a)，接受關分頁後可能無法補傳。之後加入短期補傳憑證 (b)，
與 Review Grant 分開。本手冊不修改已接受的 ADR。

PR #27（伺服器宣布場次開始後才錄影、Leave 按鈕、IndexedDB 錯誤說明）仍未合併；
合併前，學生端仍會在加入場次、相機可用後開始錄影。

## 學生端操作

1. 加入指定場次，允許相機和麥克風，確認出現 REC 並有片段上傳。
2. 正常結束時按 Stop REC，保持同一分頁開啟。
3. 離線時會顯示待傳或失敗片段。恢復連線後讓它自動重試；不要清除網站資料、
   IndexedDB 或改用另一個場次上傳原有片段。
4. **只有顯示「可以安全關閉」後，才可關閉分頁。** 佇列暫時清空、Stop REC、
   session 已結束或沒有紅色錯誤，都不等於伺服器已確認 complete。
5. 顯示中斷、不完整、需要管理員，或長時間沒有進展時，立即通知 operator，
   提供 session ID 和畫面狀態，保留原分頁與網站資料。

### 重新整理、還原分頁與重新開頁

| 操作 | 行為與限制 |
| --- | --- |
| 重新整理原分頁，憑證仍有效且保留 | 可恢復 IndexedDB 中的 pending chunks 和 finalize；不開新的 MediaRecorder |
| 還原原分頁，瀏覽器也還原了 sessionStorage 憑證 | 可嘗試相同補傳流程；是否保留憑證取決於瀏覽器，不能一概保證 |
| 正常 Stop 且最後 chunk、finalize 已持久化，再關分頁 | 同瀏覽器、同 profile、同 origin 可用 OP 補傳碼恢復原 IndexedDB 佇列；仍受授權及寬限期限限制 |
| 換瀏覽器、profile 或 origin（包含 port） | 不會自動取得原 IndexedDB；補傳碼不會搬移影片或重建遺失片段 |
| 錄影中重新整理，原 recorder 已遺失 | 顯示錄影中斷並提交 recorder_lost；舊錄影保持 incomplete，即使已有片段全部補齊 |
| 已確認 complete 後重新整理 | 應保留完成狀態，不重新錄影；仍依現有憑證及還原流程處理 |

一個 session 在 Phase 1 只有一次錄影。需要重新錄製時由 OP 建立新 session 和
新 join code；舊場次與其媒體保留，不把新錄影接在舊片段後面。

**一次性 join code 已使用後不能重播來恢復 token。** 沒有原憑證時不要反覆加入，
也不要把 live token 長期存進 localStorage／IndexedDB、放到 URL，或以另一角色繞過認證。
依下面的短期補傳流程處理；不要把 OP token 給學生。

### 關閉分頁後：Resume upload

1. 使用原來的瀏覽器、profile 和前端 origin 開啟 Student。沒有 sessionStorage
   憑證但有未完成佇列時，會顯示 Resume upload。
2. **畫面的 session ID 綁定舊錄影，不能改成新場次 ID。** 把這個 ID 提供給 OP，
   由 OP 確認資料與期限後發一次性補傳碼。
3. 在表單輸入補傳碼，進入只補傳畫面。這不會建立新場次或新 MediaRecorder，
   也不會把不完整的錄影變成完整錄影。
4. 保持網路與分頁，等伺服器確認 complete、畫面顯示「可以安全關閉」。
   若仍有非認證終態錯誤，重新登入也不會解除，須交 OP 處理。
5. 若要加入另一個場次，選 Join another session 回一般加入畫面；此操作保留
   舊佇列，不把舊片段送到新場次。已確認 incomplete 且沒有 pending 工作的場次
   不會強迫學生停留在補傳碼畫面。

錄影中直接關閉或重新整理仍走 `recorder_lost`，不是正常 Stop 後的補傳情境。
即使原有片段全數送達，也保持 incomplete，不重新開錄。

## Operator：一次性補傳碼

**一般做法：用 OP 管理頁。** 以管理員帳號登入，在場次列表選擇該場次。右邊「錄影狀態」
顯示場次狀態、結束時間、補傳寬限剩餘、錄影／finalize 狀態、已存片段及兩次讀取的進度
比較。確認學生仍在用保存原資料的瀏覽器後，按「發補傳碼」。補傳碼只顯示一次，透過可信任的
管道交給學生，交妥後按「已轉交，從這個分頁清除」。

**後備做法：API。** 只有 OP 可呼叫 `POST /sessions/{id}/upload-reissue`。Bearer 可以是靜態
operator token，也可以是管理員登入取得的 token（見 spec 修訂 12）。以下沿用下一節的
`$apiBase`、`$sessionId`、`$headers`；只在可信任的 OP 終端執行：

```powershell
$issued = Invoke-RestMethod -Uri "$apiBase/sessions/$sessionId/upload-reissue" -Method Post -Headers $headers
$issued | Select-Object expires_at, recording_state, stored_sequences, seconds_since_last_chunk
```

回應另有 `upload_code`，明文只在發碼回應出現一次。由 OP 透過可信任管道把
`$issued.upload_code` 交給該學生；不寫進文件、URL、公開 log 或 Git。
`stored_sequences` 是已存片段的數量；`seconds_since_last_chunk` 是距最後片段的秒數，
無片段時為 null，不能單憑它判定 recorder 已遺失。

學生表單以 `POST /sessions/{id}/upload-login`、JSON `{"code":"補傳碼"}` 換取
`access_token`、`token_type=upload`、`role=student`、`expires_at`，此交換不需要
Bearer。取得的 `typ=upload` token 只授權同一 session 的三個操作：

| 操作 | 端點 |
| --- | --- |
| 上傳原片段 | `POST /recording/{id}/chunk` |
| 提交原 finalize | `POST /recording/{id}/finalize` |
| 查精簡上傳狀態 | `GET /recording/{id}/status` |

它不授權 WS、案件資料、教師審閱或 process。不要把學生補傳憑證當成 review token。

- 一次性碼期限 10 分鐘；upload token 最多 15 分鐘。session 已結束時，token
  不能超過 `ended_at + MINDPROBE_UPLOAD_GRACE_SECONDS`（預設 600 秒）。
  結束前發出的 token 也在後續請求檢查寬限期，不能靠較晚的 exp 延長期限。
- `created/starting/active/paused` 可發碼；session 尚無 ended_at 時，600 秒尚未開始。
  發碼不撤銷原 live token，也不重設錄影、ended_at 或寬限期限。
- 正常 `/end` 不設定安全撤銷旗標；安全撤銷則透過
  `upload_grants.security_revoked_at` 阻止發碼、兌換及使用。
- 超過寬限期時 reissue 回 `409 upload_grace_expired`。不要重設期限、改資料庫狀態
  或用新 session 的憑證繞過；保留 pending 媒體與 incident，交 OP 決定後續處理。
- 發碼與兌換有速率限制；失敗時先查狀態及回應，不連續嘗試已用過的碼。

## Operator：辨識疑似卡住的錄影

目前沒有完整監控頁。OP 管理頁的場次列表和「錄影狀態」已涵蓋下表的欄位，並會比較兩次
讀取的進度；下面的 API 寫法是後備做法。OP 應保留建立場次時的 session ID 清單逐一查詢；不依賴 Student 的 SESSION 標籤、瀏覽器時鐘 offset 或是否看到警示來判斷完整性。

在可信任的 OP 終端查詢，不把 operator token 發給學生。以下使用既有的
`MINDPROBE_OPERATOR_TOKEN` 環境變數；API 位址請使用該環境的 HTTPS 位址。

```powershell
$apiBase = 'https://YOUR-API-HOST'
$sessionId = 'YOUR-SESSION-ID'
if (-not $env:MINDPROBE_OPERATOR_TOKEN) { throw 'Operator token is not configured' }
$headers = @{ Authorization = "Bearer $env:MINDPROBE_OPERATOR_TOKEN" }
$session = Invoke-RestMethod -Uri "$apiBase/sessions/$sessionId" -Headers $headers
$recording = Invoke-RestMethod -Uri "$apiBase/sessions/$sessionId/recording/status" -Headers $headers
[pscustomobject]@{
    session_id = $sessionId
    session_status = $session.status
    ended_at = $session.ended_at
    recording_state = $recording.recording_state
    finalize_state = $recording.finalize_state
    final_sequence = $recording.final_sequence
    chunk_count = $recording.chunk_count
    last_sequence = $recording.last_sequence
    missing_sequences = $recording.missing_sequences
    incomplete_reason = $recording.incomplete_reason
} | ConvertTo-Json -Depth 3
```

收到「已停止／分頁已關閉」的通知後，隔一段時間重讀狀態，例如相隔 15 秒讀兩次，
比對 `chunk_count`、`last_sequence`、`final_sequence` 及 `finalize_state`。這是人工判讀
範例，不是新增伺服器逾時規則。正常錄影中短暫沒有新片段，不能單獨判成遺失。

| 觀察 | 判讀與處理 |
| --- | --- |
| recording，finalize_state=none 或沒有 final_sequence；學生已關閉／停止，片段數不再增加 | 疑似未收到 finalize 或無法繼續補傳，立即人工追查，不要等自動通知 |
| finalizing／pending，序號缺漏仍在，但片段數持續增加 | 補傳中；保持原分頁、網路與憑證，持續觀察 |
| pending，缺漏及片段數都沒有變化，學生也無法還原原分頁 | 疑似卡住；保留資料，記錄 incident，依下方收尾流程處理 |
| finalize_state=complete | 上傳完整性已確認；不代表 FFmpeg、MP4 驗證、R2 上傳或清理已完成 |
| incomplete，原因 recorder_lost／operator_incomplete | 保持 incomplete，不因缺漏清空而改成 complete；保留 chunks，交 OP 處理 |
| 已結束且超過上傳寬限期，仍停在 recording／finalizing | 查 grace scheduler、伺服器 log、實際寬限設定及既有資料 cutover；不要手動改成 complete |
| 沒有 recording row／缺少狀態欄位，或 missing_sequences=[] 但沒有 finalize | 完整性未知；不能推論成空錄影或已完成，尾段可能未宣告 |

### 狀態不會即時通知的限制

- 瀏覽器若沒把 finalize 或 recorder_lost 送到伺服器，錄影可能一直顯示 recording，
  寬限期之前也未必通知 operator。**recording 不等於裝置仍在錄影，也不等於上傳正常。**
- 寬限期以 **session.ended_at + 實際設定的 MINDPROBE_UPLOAD_GRACE_SECONDS** 計算，
  預設為 600 秒；不是從關閉分頁或按 Stop REC 起算。
- **沒有 ended_at 的 session 尚未開始寬限期**，不應期待等 600 秒便自行收尾。
- 已結束 session 的 recording 可能仍是 recording 或 finalizing，取決於結束路徑與
  伺服器是否收到 finalize；判斷寬限期限應看 session.ended_at，不能只看 recording_state。
- grace checker 是每 60 秒執行的程序內執行緒。邊界後可能要等下一輪，
  程序停止或 scheduler 關閉時不會處理。它不是已有可靠派送機制的工作佇列或即時告警服務。
- 沒有 recording row 的舊場次還涉及 `MINDPROBE_UPLOAD_GRACE_SYNTHESIZE_AFTER`；
  依部署 cutover 設定排查，不能為了清掉畫面上的卡住狀態而任意改寫歷史資料。

### 人工收尾

1. 先詢問學生是否仍在錄影、是否保留原分頁、是否有待傳或錯誤提示；記錄上述 API 狀態。
2. 原分頁和有效憑證仍在時，協助恢復網路並觀察補傳。錄影中途遺失的 take 仍須保持 incomplete。
3. 若訓練確實已結束而 session 還沒結束，由有權限的 OP 明確結束 session，確認取得 ended_at。
   不要為了排查而結束另一個仍在正常訓練的場次。

   ```powershell
   Invoke-RestMethod -Uri "$apiBase/sessions/$sessionId/end" -Method Post -Headers $headers
   ```

4. 依實際寬限期限追蹤結果。學生可用仍有效、僅因 session_ended 撤銷的原 live token，
   或依上述流程取得的有效 upload token 補傳；兩者均不能繞過寬限期或安全撤銷。
5. 無法還原憑證或超過期限時，記錄未完成原因並保留瀏覽器、伺服器的原始媒體和 metadata。
   不手動宣告 complete、不清理 pending blobs、不拿新 session code 補舊場次。
6. 需要重新演練時，依 D11 由 OP 建新場次，舊場次獨立保留為未完成。

現有一般 `/process` 會拒絕 incomplete take。OP partial 轉檔與清理目前沒有
操作流程；不能為了取回部分影片而強制 complete 或刪除原始資料。

## 錯誤提示與網路排查

- 仍有短暫失敗片段時，學生端會保留錯誤；目前顯示的片段確認後，若另一段仍失敗便改顯示
  該段，之後成功的 status 會清除已確認片段的舊錯誤。開著的舊分頁可能仍用舊版前端，請先
  重新整理（不要在錄影中按 F5，否則會遺失 recorder），再由 OP 比對進度。0 failed 本身
  也不證明沒有終態錯誤。
- `Failed to fetch` 或 Provisional headers 本身不能確定是 CORS。先確認 API
  可達，再檢查 OPTIONS 是否允許實際前端 origin（含 port）、POST、Authorization
  和 Content-Type。`MINDPROBE_CORS_ORIGINS` 必須包含該 origin；修改後重啟 API。
  不用 wildcard 取代正式白名單。認證 401 也應帶正確的 CORS header。
- [既有 issue #4](https://github.com/erickh826/mind-probe/issues/4)：重新整理後可能顯示
  PAUSE MANUAL，API 卻仍是 recording_failure。以伺服器原因判讀，勿因此恢復舊 take。
- DevTools Offline 未必切斷已建立的 WS；HTTP 補傳成功不能當作 WS 重連已驗收。
